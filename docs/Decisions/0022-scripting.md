# 0022 - Scripting: Lua Behaviors on Entities, Reflected Components, a Sandboxed VM

## Status
Accepted

## Context
Milestone 8 adds the scripting API (entities, components, the scene, input, physics, animation), hot reload, the [sandbox](../Features/Scripting.md#sandbox), LuaLS annotations generated from the bindings with CI type-checking, and a small game built by an agent through MCP alone. Lua 5.4 with sol2 is chosen ([Decision 0001](0001-scripting-language.md)) and compiled as C++ ([Decision 0003](0003-lua-compiled-as-cpp.md)). Scripts are gameplay: they run in the simulation, on the server, and are never re-simulated for prediction ([Decision 0021](0021-physics.md)).

## Decision
- **A script is a behavior on an entity** - the `Script` component names a script asset (a `.lua` file in the project) and overrides its properties. The file returns a table: callbacks (`OnCreate`, `OnUpdate(dt)`, `OnDestroy`, `OnCollisionBegin(other)`, `OnCollisionEnd(other)`, `OnTriggerEnter(other)`, `OnTriggerExit(other)`, `OnReload`) and default `Properties`. Each entity gets an instance, a table whose fields start as the properties and whose metatable is the script's table, so `self` holds the entity (`self.Entity`), its properties and whatever the script keeps. One script per entity; more behaviors go on child entities
- **Properties from the component** - `Script.Properties` is a JSON object overriding the defaults (`{"Speed": 6, "Up": "W"}`): numbers, booleans and strings, and arrays of 2 to 4 numbers for vectors. A value of the wrong type, or for a property the script doesn't declare, is reported and ignored. JSON keeps the component a reflected string, editable in the inspector and by MCP like any field
- **The scripting system runs in the simulation** - before physics, it creates instances for new `Script` components (`OnCreate`), destroys those whose entity or component went away (`OnDestroy`), and calls `OnUpdate` in the order of the components; after physics it delivers the tick's collision and trigger events to both entities' scripts. Animation advances after both. An instance's own fields aren't snapshotted: rollback restores components, and scripts keep what must survive it in components. Clients don't run gameplay scripts, so prediction never needs them
- **Components through reflection** - `entity:Get("RigidBody")` returns a proxy whose fields read and write the component through the reflection registry, with its limits and read-only flags enforced, so every registered component is scriptable without bindings of its own, and new ones are as they're registered. Required components can't be added or removed, internal ones aren't visible, and the hierarchy changes through `SetParent`
- **The API** - globals: `Scene` (create, find, instantiate prefabs, destroy), `Input` (keys, mouse and gamepads of a player's input command), `Physics` (raycasts, impulses, sleeping), `Animation` (play, crossfade, stop, speed, clips by name or index), `Time`, `Log`, and the math types `vec2`, `vec3`, `vec4` and `quat`; `Entity` handles (name, components, hierarchy, world transform, script instance). Functions are PascalCase like the engine's; vector components are lowercase like glm's. Audio, UI and networking join in their milestones
- **The sandbox** - as [Scripting](../Features/Scripting.md#sandbox) specifies: only `base` (without `dofile`, `loadfile` or binary `load`), `string`, `table`, `math`, `utf8`, `coroutine` and three `os` functions; `require` loads the project's scripts by module name (`require("Scripts.Util")` is `Assets/Scripts/Util.lua`) and nothing else; a memory limit in the allocator; and an instruction budget per callback, checked by a count hook, after which every check raises again so `pcall` can't outlast it. Errors are logged with the script, line and traceback, and the instance that raised one gets no more callbacks until scripts reload
- **Deterministic by default** - Lua's string hash seed is fixed at build time (it otherwise mixes in the clock and addresses), and `math.random` is seeded the same way for each run, so the same state and input give the same result, as the simulation requires ([Decision 0012](0012-simulation-and-rollback.md)). Iterating tables keyed by tables or functions still follows addresses: scripts that need an order sort or use arrays
- **Hot reload** - the editor watches the script files play mode loaded; when one changes, every script module is loaded again and each instance's metatable swapped for its script's new table, keeping the instance's fields, then `OnReload` is called. An instance disabled by an error runs again. A script that fails to load keeps its old version and reports why
- **Annotations generated from the bindings** - the engine writes LuaLS annotations: the hand-written API declarations (`LuaApi.lua`, embedded at build time), plus a class for every registered component with its fields' types and descriptions, `Entity:Get` and `Entity:Add` overloads typed for each, and the names of components, keys, buttons and axes. Opening or creating a project writes them to `.lodestone/Lodestone.lua`, and a `.luarc.json` if it has none; MCP gives agents the text. The test scripts' project and the samples have theirs committed, and a test keeps them the same as the engine's output. CMake fetches lua-language-server 3.19.1 (MIT, pinned and hashed, like lavapipe) and a test type-checks the test and sample scripts against the annotations, failing on any warning; another runs it on scripts full of marked mistakes, which it must find exactly. The test scripts call every annotated function, which a test checks - and another that every function scripts can reach is annotated - so the test scenes exercise the whole API
- **Physics queries see the latest step** - raycasts and sleep checks ask the physics world as the latest physics step left it, so what a script creates or moves this tick joins it when physics runs. Play mode syncs the world with the scene when it starts, so the first tick's scripts can query the level. Syncing the world for every query would cost a pass over the scene's bodies each time
- **The editor** - play mode runs scripts after the play systems and before physics, and delivers physics' events to them after it; stopping ends every instance (`OnDestroy`) on the play scene before it's restored. It checks the loaded scripts' files twice a second (by write time and size) and reloads when one changed. MCP gains `script_write` (create or replace a script, compiled first so syntax errors come back with their line, reloading at once in play mode), `script_read` and `script_api` (the annotations); errors land in the console and `log_read`
- **What the sample game showed** - building Pong through MCP alone found two gaps, now closed: rotations had to be given as quaternions, so the editing commands also take Euler angles in degrees (`{"degrees": [x, y, z]}`, the inspector's convention, converted precisely near gimbal lock by `Rotation.h`); and screenshots came only from the editor camera, so `viewport_screenshot` can render from the scene's primary camera, without the overlay, as the game shows it

## Alternatives
- **Script state snapshotted with the simulation** - serializing every instance's table every tick is expensive, fails on functions and userdata, and serves no consumer: the server never rolls back and clients don't run gameplay scripts
- **Several scripts per entity** - flexible, but a component can't repeat on an entity, and child entities serve the same purpose
- **Typed property fields in the reflection registry** - per-script fields would make component types dynamic; JSON in one field keeps reflection static
- **Per-component bindings** - better performance for hot fields, but every component would need code; reflection is enough at this scale, and specific bindings can be added where profiling shows a need

## Consequences
- Writing a vector field's component (`t.Position.x = 1`) changes a copy; scripts assign whole values (`t.Position = vec3(1, 0, 0)`)
- Scripts can't steer the built-in character controller's prediction; they move it through its components, on the server
- A fixed hash seed lets crafted strings collide on purpose; the instruction budget bounds what that can cost
- A raycast in the same tick as a body is created or moved misses the change; scripts that need it wait a tick
- New instances can call each other from `OnCreate`, but the one called may not have run its own `OnCreate` yet
